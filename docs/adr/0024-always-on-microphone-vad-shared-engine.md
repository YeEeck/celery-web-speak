# 状态检测复用常开麦克风 VAD 引擎，改写静音说话提醒的采集边界

静音说话提醒设计（muted-speaking-reminder-design.md）原定"仅语音会话内采集、离开语音立即停止"。在线状态检测需要随时可用的说话信号，而麦克风授权在登录后即已获得。决策：授权后 VAD 引擎常开运行（一条麦克风流、一个 libfvad worker），产出说话事件流；静音说话提醒降级为该引擎的消费者，保留其原有门控（语音 connected + 主动静音 + 开关 + 提示音开启）不再自持 VAD。

这改写原设计文档的采集边界：麦克风在登录后持续采集，即使用户从未加入语音。隐私代价换取全场景覆盖；拒绝麦克风权限的用户没有自动检测（状态点退化为连接存活语义），不为此新增权限请求。原设计中"关闭提醒或离开语音时停止 VAD，避免没有可见收益的持续计算"的资源规则随之失效——状态检测给予了持续计算的可见收益。

引擎生命周期由应用级驱动（登录 + 麦克风授权），不采用消费方引用计数：授权后启动、退出登录或权限丢失时停止，首选输入设备变化时重启采集；消费方（在线状态检测、静音说话提醒）只订阅说话事件流。引用计数方案（最后一个消费方停止时释放）因在线状态检测始终持有引用而形同虚设，且消费方启停对账错误会中断常开采集——曾在离开语音时误停引擎。引擎启动失败后保持停摆，在标签页恢复可见、设备变化或权限重新授予时自动重试。

## 修订（2026-08-03）：采集设备约束一律 `{exact}`，并发启动加守卫

Chromium 在部分平台（Linux/PulseAudio）上存在设备解析怪癖：省略 `deviceId` 或以字符串（ideal 约束）传 `'default'` 时，`getUserMedia` 会解析到浏览器自身的默认输入（实测落到枚举首位的静音设备——Pico 扬声器麦阵列），只有 `{exact: 'default'}` 才解析到操作系统默认输入。引擎采集因此长期在浏览器端吃到静音源，而发布链靠 LiveKit 连接后的 `switchActiveDevice({exact})` 路径偶然绕开。引擎采集约束与发布链统一为 `deviceId: { exact: ... }`（含 `'default'`）。另发现生命周期 `sync()` 在引擎异步启动窗口内连续触发可开出多条并发采集流，`start()` 增加进行中启动复用守卫。VAD 采集的 AGC 设置变更见 ADR-0012 修订。
