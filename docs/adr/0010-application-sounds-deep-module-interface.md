# 以领域事件与设置控制投影深化应用提示音 module

应用提示音原先以按事件展开的 Pinia ref、细粒度 setter 和播放机制参数作为 interface，导致设置界面重建事件槽状态，业务调用方还必须知道主动退出绕过限流等播放政策。决定将其深化为一个以领域事件 `signal`、应用提示音设置控制投影和播放上下文同步组成的 interface；implementation 统一拥有操作提示音事件槽、静音说话提醒的固定反馈、来源不变量、异步操作顺序、持久化 adapter、解码缓存、限流、输出路由和浏览器播放生命周期。语音与消息 module 仍负责判定真实领域事件，应用提示音 module 不接收原始状态变化，只决定合格事件到声音反馈的政策。`signal` 始终使用最后一次已提交且可播放的状态；启动加载或配置变更期间不等待异步操作，也不延迟补播，尚未验证的自定义来源暂以该槽保留的系统预置音效反馈。

考虑过 `state + configure + play` 的最小通用 interface，以及暴露 mutation、revision、pending 和输出状态的扩展型 interface。前者会让通用命令联合类型随能力增长，后者会把内部协调状态泄漏给调用方；按调用意图区分 interface 能让业务调用方只报告领域事件，让设置界面直接使用同形事件槽，同时把浏览器存储与 Web Audio seam 留在 module 内部。

用户主动发起的设置与试听失败由对应设置控制投影返回并保存结构化问题，且不覆盖此前已提交状态；后台领域事件播放和输出设备回退失败不穿过 interface，不阻塞业务流程，只进入诊断记录。由此避免业务调用方处理无法补偿的音频错误，同时让设置界面对用户刚刚发起的失败操作给出准确反馈。

为避免语音 module 重新组合总开关、音量与耳机静音政策，应用提示音 interface 提供一个只读的静音说话提醒可发声投影。语音 module 只把该结果与语音连接、主动麦克风静音、服务器语音禁言、提醒独立开关和麦克风权限组合，不由应用提示音 module 反向控制 VAD 生命周期。

启动加载、浏览器首次交互解锁和资源清理由 implementation 随 Pinia store 的创建与销毁管理，不在 external interface 暴露安装、卸载或启动顺序。根应用不再协调应用提示音生命周期，测试则通过内部浏览器交互 adapter 控制可播放状态。

浏览器存储、音频执行、交互状态与时钟采用 module 内部 seam：生产分别使用浏览器 adapter，测试使用内存或可控 adapter，但两者都通过同一个 external interface 验证行为。竞态、来源修复、播放政策和错误投影不再依赖直接访问 Pinia 私有状态、缓存或 IndexedDB helper 的测试；真实浏览器测试只保留存储和 Web Audio 接线的集成覆盖。

`localStorage` 与 IndexedDB 不增加跨存储事务日志。上传或替换先写入已验证音频、再选择自定义来源；删除先移除音频、再选择系统预置音效，运行中只发布完整成功的状态。浏览器若在两次写入间终止，下次启动通过来源归一化恢复到合法且可播放的状态；接受无法完整回滚崩溃前用户意图的代价，避免为三个独占事件槽引入 journal 或两阶段提交。
