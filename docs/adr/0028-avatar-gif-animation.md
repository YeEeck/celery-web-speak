# 头像支持 GIF 动图：跳过裁剪器原字节直传，校验契约按格式分化

用户要求头像支持 GIF 动图。决策：客户端选中 GIF 时**跳过 ImageCropperModal**（canvas 输出会拍平动画）原字节直传服务器，展示端 `UserAvatar` 的 `<img>` 天然渲染动画、零改动。服务器校验参数化——校验函数按用途接收允许 MIME 集合：头像白名单在 {image/png, image/jpeg, image/webp} 基础上新增 `image/gif`（Go 标准库 `image/gif` 自带注册，仅需空导入、零新依赖），服务器图标维持原白名单不变。契约分化：GIF **放宽 1:1 正方形约束**（旁路裁剪器后无方形保证，圆形遮罩 + `object-fit: cover` 显示任何比例均成立），PNG/JPEG/WebP 保持 1:1±0.02；维度 ≤1024×1024 不变；上传总量上限全局 4MB→8MB（静态格式经裁剪器输出仅约 100KB，上限对它们形同虚设；动图常见 5-15MB）。存储（SQLite BLOB）与缓存机制（`avatar_version` + `immutable`）与 MIME 无关，原样沿用。

## Considered Options

- **帧级裁剪后仍输出动图**：浏览器无原生动图裁剪 API，需引入第三方 GIF 编解码库逐帧裁切再合成，复杂度高一个量级；收益仅为"上传时能裁 GIF"。舍弃。
- **裁剪后输出静态**（首帧 WebP）：等于否定动图头像。舍弃。
- **服务器图标一并放行 GIF**：共享校验路径 `readImageUpload`/`validateImageHeader` 若直接加白名单，服务器图标在服务端呈"半放行"（客户端 `accept` 仍挡）的隐式状态；参数化按用途传允许集合，代价一个参数。舍弃——需求未提服务器图标，以后需要再放行。
- **GIF 保持 1:1 强制**：裁剪器旁路后 1:1 已无契约基础，只会拒绝大量非方形常见动图。舍弃。
- **限制 GIF 帧数**：需完整解码（1024²×4B×帧数，百帧数百 MB 内存），违背"仅校验不二次编码"姿态。舍弃——靠 8MB 字节上限 + 1024 维度上限兜底。
- **上传上限按格式分档**（GIF 8MB、其余 4MB）：多一套分支，收益不值。统一 8MB。
